zed-fireworks

Status: live-system, maintained — the tool runs from a daily systemd user timer and its actual behavior is the committed script (dl-selfregime).
Locked: models.dev as the catalog source (dl-catalog), Zed's openai_compatible.fireworks provider as the target (dl-target), the full capability set (kp-caps), the merge order (kp-merge), JSONC splice preservation (dl-jsonc), the atomic write (kp-write), and one stdlib-only file (dl-stdlib).
Open: watch-capability-set, watch-effort-menu, watch-output-limit (Open Items).
Top risk: an upstream catalog or Zed schema change lands after a sync, so the timer writes a rejected or incomplete settings file (watch-capability-set).

Read every line of this file before acting; it is the load unit. With the tool installed, begin with python3 lspec.py start zed-fireworks-spec.html.

Ethos: treat Zed's settings file as a guest: change only the one managed array, assert every contract before writing, and leave a recoverable backup whenever the content changes.

Conventions: read this file whole before acting; it is the only file in the collection. Every value lives once in Key Parameters or is indexed from its authority: actual behavior is zed-fireworks-sync.py at its version line; required behavior is the rows below and the Decision Log; conformance evidence is a --dry-run output or the backup. Status tokens, one per axis: confirmed(source) / provisional(source); locked / open; WATCH. Inline [WATCH] markers link a watch entry; dates live there, not inline. Git holds history; body text is present tense and links to rationale. Decisions use dl- row ids; each row opens its first cell with that id in <code>, uncounted; each cell is at most 40 words. Replace a superseded row, keeping the displaced choice in its successor's rejected/replaced cell. Retain a row only if a fresh session might re-propose its rejected alternative. For an assumption-dependent lock, name the assumption and reopening condition. Change the scope fence and log the decision before reintroducing an excluded option. A change to a data-sealed claim is a decision change, recorded in a dl- row in the same commit, or a correction with its reason naming the decision it restores, else confirmed by a later session's review: commit naming it.

Session: load → make one move → update the canonical state → reconcile touched claims and their one-hop neighbors → commit → confirm a clean working tree. Check referrers, cited evidence, copies, counts, status, declared counterparts, dependents, and indexed artifacts; follow up only into neighbors changed by the fixes. Report a missing instruction referent; state your interpretation and clarify if alternatives would materially change the edit. If you cannot ask, take the reading that changes least and record the alternative as an open item. Commit types: docs feat fix seed audit review; each subject is one typed transition line pointing to rationale, never restating it. Seed and review bodies may carry assessments.

Dependencies: put <a rel="depends-on" href="#target"> inside the dependent claim. Its nearest id'd ancestor names that claim. Both anchors enclose complete claims: a paragraph, section, or table row; a heading covers only its title. Plain links are navigation. The collection is one file, so a dependency stays in-file. A changed or missing target owes review: confirm or fix the dependent and record it in a review: commit naming the claim, or in the target's own commit when its gate confirms the dependent unchanged. Removing or redirecting a dependency of a surviving claim takes a review; deleting the dependent claim retires its obligations. Uncommitted edits clear nothing. Review history lives in git.

Tooling: begin with python3 lspec.py start zed-fireworks-spec.html and follow its output. Without the tool, perform its checks by hand. This instance carries its own copy of lspec.py and hooks/; never link a methodology repository in their place.

Out of Scope

  • Reading, storing, or proxying API keys; Zed's provider credentials are untouched.
  • Managing any other setting, keymap, theme, or non-Fireworks provider.
  • Importing OpenCode runtime logic or guaranteeing account access and tool execution.
  • Installing timers on non-systemd or non-Linux systems; the sync itself stays portable.
  • Validating model-specific reasoning-effort levels; Zed's menu is generic.

Record

Git is the record: every session-event is a commit; every full sweep takes an audit: commit, empty only when no files change. A clean sweep may update bookkeeping. No in-file history; the script's module docstring carries the artifact version.
